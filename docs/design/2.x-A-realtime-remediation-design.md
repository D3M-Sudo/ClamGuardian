# CLAMGUARDIAN — 2.x-A REALTIME REMEDIATION DESIGN

---

## 1. Executive Summary

An independent architectural and implementation audit of ClamGuardian's 2.x-A Realtime Subsystem (`clamguardian/realtime/`) evaluated the subsystem as **NOT READY / BLOCKED**. Three P1 defects were confirmed:

1. **P1-REALTIME-DEBOUNCE**: Debounce evaluation is pull-driven. Events are evaluated for debounce expiration only when `handle_events()` is called again. If no subsequent event arrives, pending debounced scans never execute.
2. **P1-REALTIME-QUEUE-BOUND**: `max_queue_depth` limits only `_pending_events`, but upon debounce expiration, `asyncio.create_task()` creates active scan tasks without enforcing a matching backlog bound. Under event storms, active tasks can grow bounded only by available system memory.
3. **P1-REALTIME-RECURSIVE-WATCH**: `InotifyMonitor.add_watch()` registers only the target directory itself via `inotify_simple`. Subdirectories and newly created nested folders are not registered, causing events inside nested folders to be completely missed.

This document presents a **technical remediation design and implementation plan** to resolve all three P1 issues without modifying core subsystem boundaries or expanding scope into 2.x-B / 2.x-C features.

## 4. Current Failure Modes

### 4.1 Debounce Failure Mode (Pull-Driven)
In `RealtimeScanOrchestrator.handle_events(events)`:
```python
# Lines 63-68 of orchestrator.py
ready_paths = [
    p for p, ts in list(self._pending_events.items())
    if (now - ts) >= self.debounce_seconds and p not in self._active_scans
]
```
If event $E_1$ for file $A$ arrives at $t_0$, `_pending_events[A]` is set to $t_0$. If no further call to `handle_events()` occurs, `ready_paths` is never re-evaluated. File $A$ is never scanned.

### 4.2 Queue Backpressure Failure Mode
In `RealtimeScanOrchestrator.handle_events(events)`:
```python
# Lines 55-58 of orchestrator.py
if (
    len(self._pending_events) >= self.max_queue_depth
    and path not in self._pending_events
):
    continue
```
When debounce expires, `_pending_events.pop(path)` removes the path from `_pending_events` and spawns `asyncio.create_task(self._execute_scan(path))`. `_active_scans.add(path)` is updated, but `len(_pending_events)` drops by 1, allowing new pending events to enter while active tasks accumulate up to the runner's internal semaphore buffer. Under 10,000 events across 500 paths, hundreds of `asyncio.Task` instances sit awaiting `ScanTaskRunner._semaphore`.

### 4.3 Recursive Watch Failure Mode
In `InotifyMonitor.add_watch(path)`:
```python
# Lines 38-42 of inotify.py
resolved = Path(path).resolve(strict=True)
wd = self._inotify.add_watch(str(resolved), self._mask)
self._wd_map[wd] = resolved
```
Inotify is non-recursive at the Linux kernel level. Adding `/watch_dir` watches only entries directly inside `/watch_dir`. Any directory `/watch_dir/subdir` is ignored unless explicitly registered with its own watch descriptor ($wd$).

## 5. Approved Architectural Decisions

1. **Push-Driven Debouncing**: `RealtimeScanOrchestrator` will manage active timer handles using `asyncio.get_running_loop().call_later(...)` or dedicated timer tasks per path.
2. **Unified Backpressure Invariant**:
   $$\text{unique\_pending\_paths} + \text{scheduled\_unacquired\_tasks} + \text{active\_scans} \le \text{max\_queue\_depth}$$
3. **Dynamic Recursive Inotify Watch Registry**: `InotifyMonitor` will maintain bidirectional mappings (`wd <-> Path`), perform an initial recursive directory tree walk on `add_watch()`, and dynamically attach watches upon observing `CREATE|ISDIR` or `MOVED_TO|ISDIR` events.
4. **Strict Scope Preservation**: No changes to `ScanTaskRunner` contract, core models, engine interfaces, GTK UI, or SQLite databases.

## 6. Debounce Remediation Design

### 6.1 Timer Mechanics & Ownership
`RealtimeScanOrchestrator` will own a private dictionary of active debounce timer handles:
`_debounce_timers: dict[Path, asyncio.TimerHandle]`

When an event for `path` passes policy checks:
1. If `path` is already in `_active_scans`, the event is ignored or recorded for post-scan re-trigger according to policy.
2. If `path` has an existing timer in `_debounce_timers`, `timer.cancel()` is called to reset the quiet period (trailing edge debounce).
3. If total backlog (`len(_pending_events) + len(_active_scans)`) is at `max_queue_depth` and `path` is not already pending, the event is dropped (or counted as dropped).
4. A new timer is scheduled using `loop.call_later(self.debounce_seconds, self._on_debounce_expired, path, on_complete)`.

### 6.2 Lifecycle & Expiration Callback
```python
def _on_debounce_expired(self, path: Path, on_complete: Callable[[ScanResult], None] | None) -> None:
    asyncio.create_task(self._dispatch_scan(path, on_complete))
```
`_dispatch_scan(path, on_complete)`:
1. Acquires `self._lock`.
2. Removes `path` from `_pending_events` and `_debounce_timers`.
3. Adds `path` to `_active_scans`.
4. Invokes `await self._execute_scan(path, on_complete)`.
5. In `finally:`, removes `path` from `_active_scans`.

### 6.3 Shutdown Semantics
On `orchestrator.close()` or `shutdown()`:
1. Cancel all active timer handles in `_debounce_timers.values()`.
2. Clear `_debounce_timers` and `_pending_events`.
3. Cancel or await in-flight `_active_scans` via `runner.cancel_all()`.

## 7. Queue / Backpressure Design

### 7.1 Formal Capacity Invariant
At all times $t$, the system enforces:
$$\mathcal{B}(t) = |\text{Pending Paths}| + |\text{Active Scans}| \le \text{max\_queue\_depth}$$

- **Pending Paths**: Paths with an active debounce timer awaiting expiration.
- **Active Scans**: Paths that have expired debounce and are currently submitted to `ScanTaskRunner` (either waiting on `ScanTaskRunner`'s concurrency semaphore or currently scanning in ClamAV).

### 7.2 Event Storm Coalescing & Rejection Rules
For an incoming event $E$ on path $P$:
- **Case 1: $P \in \text{Pending Paths}$**
  - Reset debounce timer for $P$.
  - Backlog count $\mathcal{B}(t)$ remains unchanged.
- **Case 2: $P \in \text{Active Scans}$**
  - Mark $P$ as "dirty" / pending re-scan upon completion, OR coalesce if re-scan queue is full.
- **Case 3: $P \notin (\text{Pending Paths} \cup \text{Active Scans})$**
  - If $\mathcal{B}(t) < \text{max\_queue\_depth}$: Accept $P$, add to pending, schedule timer. $\mathcal{B}(t) \leftarrow \mathcal{B}(t) + 1$.
  - If $\mathcal{B}(t) \ge \text{max\_queue\_depth}$: Reject/drop event $E$, increment dropped event metric counter `_dropped_events_count`.

## 8. Recursive Inotify Design

### 8.1 Watch Registry State
`InotifyMonitor` maintains:
- `_wd_map: dict[int, Path]`: Maps watch descriptor to resolved directory path.
- `_path_map: dict[Path, int]`: Reverse mapping for quick lookup and removal.
- `_root_watches: set[Path]`: Top-level user-requested watch roots.

### 8.2 Initial Tree Registration
In `InotifyMonitor.add_watch(path)`:
1. Resolve `root_path = Path(path).resolve(strict=True)`.
2. Walk the directory tree using `os.walk(root_path, followlinks=False)`.
3. For each directory `dirpath` (including `root_path`):
   - Add inotify watch with mask:
     `CLOSE_WRITE | CREATE | MOVED_TO | DELETE | MOVED_FROM | EXCL_UNLINK | ONLYDIR`
   - Store $wd \leftrightarrow \text{dirpath}$ in `_wd_map` and `_path_map`.
   - Handle `PermissionError`, `FileNotFoundError`, or inotify limits (`OS Error: ENOSPC`) gracefully without crashing the monitor process.

### 8.3 Dynamic Subdirectory Registration
When `read_events()` parses raw inotify events:
- If `mask & flags.ISDIR` and `event_type in (CREATE, MOVED_TO)`:
  - Automatically invoke internal `_add_watch_rec(item_path)` to register the new subdirectory and any files/folders created inside it during the race window between creation and watch attachment.
- If `mask & flags.IGNORED` or `event_type is DELETE` on a watched directory:
  - Clean up corresponding $wd$ from `_wd_map` and `_path_map`.

## 10. Concurrency & Race Analysis

| Race Scenario | Risk | Mitigation Design |
| :--- | :--- | :--- |
| **Timer fires while new event arrives** | Race between `_on_debounce_expired` and `handle_events`. | Both operations execute under `asyncio.Lock()` (`self._lock`). |
| **Directory created and populated simultaneously** | Files created in `new_dir` before `add_watch` attaches. | `_add_watch_rec` performs a post-watch attachment directory scan to catch existing files. |
| **File deleted during debounce window** | Scan task attempted on missing path. | `_execute_scan` checks `path.exists()` and returns structured `ScanStatus.ERROR` result without throwing. |
| **Shutdown during active debounce timers** | Orphaned background timers or pending tasks. | `close()` explicitly cancels all `TimerHandle` objects and awaits `runner.cancel_all()`. |

---

## 11. Shutdown & Cancellation Model

1. **Monitor Shutdown (`InotifyMonitor.close()`)**:
   - Closes inotify file descriptor `_inotify.close()`.
   - Clears `_wd_map` and `_path_map`.
2. **Orchestrator Shutdown (`RealtimeScanOrchestrator.close()`)**:
   - Acquires `self._lock`.
   - For all `timer` in `_debounce_timers.values()`: `timer.cancel()`.
   - Clears `_debounce_timers` and `_pending_events`.
   - Invokes `await self.runner.cancel_all()`.

## 14. Performance / Resource Model

- **Timer Memory**: ~100 bytes per `asyncio.TimerHandle`. At `max_queue_depth=1000`, peak memory for timers $< 150 \text{ KB}$.
- **Inotify Watch Descriptors**: Default Linux kernel limit `/proc/sys/fs/inotify/max_user_watches` is typically 8192–524288. `InotifyMonitor` catches `OSError (ENOSPC)` and logs warning if watch limit is reached.
- **CPU Overhead**: Zero polling overhead during quiet periods due to event-driven `select.select()` and native `asyncio` event loop scheduling.

## 18. Acceptance Criteria

1. **P1-REALTIME-DEBOUNCE**: An isolated filesystem event automatically triggers a scan after `debounce_seconds` without requiring any subsequent event.
2. **P1-REALTIME-QUEUE-BOUND**: Total backlog (`len(_pending_events) + len(_active_scans)`) never exceeds `max_queue_depth` during event storms.
3. **P1-REALTIME-RECURSIVE-WATCH**: File creation/modification in deeply nested subdirectories under a watched root generates normalized `FileEvent` objects.
4. **Clean Verification**: All existing and new tests pass; `ruff` and `mypy` pass without errors.

---

## 19. Risks & Deferred Items

- **High-Density Directory Trees**: Subtrees with $> 50,000$ subdirectories may hit Linux `max_user_watches`. *Mitigation*: Gracefully catch `ENOSPC` and log a warning.
- **Scope Deferral**: 2.x-B `fanotify`/`clamonacc` and 2.x-C D-Bus services remain explicitly out of scope for 2.x-A remediation.
